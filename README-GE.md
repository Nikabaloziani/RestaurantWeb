# RestaurantOS — გასწორებული ფრონტი

ეს არის ბოლო გამოგზავნილი მოქმედი ფრონტის სრული ასლი შესწორებებით.
ბექის, მონაცემთა ბაზისა და Railway-ის პარამეტრები ამ არქივში არ შედის.

## გაშვება

1. არქივი ამოიღე ახალ საქაღალდეში, მაგალითად `RestaurantOS-frontend-fixed`.
   ძველი პროექტი შეინახე. აქ `package.json` პროექტის მთავარ საქაღალდეშია,
   ხოლო `App.tsx`, `pages`, `api` და დანარჩენი კოდი — `src`-ში.
2. ბექზე გამოიყენე ადრე მოწოდებული `RestaurantOS-backend-fixes.zip`-ის შესწორებები.
3. ბექი გაუშვი მხოლოდ ერთხელ, Visual Studio-დან ან PowerShell-იდან.
   კონსოლში უნდა გამოჩნდეს `Now listening on: http://localhost:5109`.
4. ამ ახალი ფრონტის საქაღალდეში, სადაც `package.json` დევს, გახსენი Terminal და გაუშვი:

```powershell
npm ci
npm run dev
```

გახსენი ტერმინალში ნაჩვენები მისამართი. ჩვეულებრივ ის `http://localhost:5173` იქნება.
შემოწმებული გარემო: Node.js 24.22.1.
ადგილობრივად `.env` საჭირო არ არის: `/api` მოთხოვნებს Vite აგზავნის localhost:5109-ზე.
თუ სხვა პროექტიდან გადაიტან `.env`-ს, `VITE_API_URL` სხვა ბექზე არ უნდა მიუთითებდეს,
თუ სწორედ იმ ბექთან დაკავშირება არ გინდა.

## რა შეიცვალა

- ყველა API მოდული ერთნაირად იყენებს `VITE_API_URL`-ს. ადრე ბილინგი და
  თანამშრომლების ნაწილი ამ მნიშვნელობას იყენებდა, ხოლო შეკვეთები და ავტორიზაცია
  development რეჟიმში უგულებელყოფდა. შესაძლებელი იყო სხვადასხვა ბექზე მოთხოვნების გაგზავნა.
- მოლარეს აღარ უჩანს შეკვეთის შექმნისა და სტატუსის შეცვლის მოქმედებები.
  გადახდის ჩაწერა კვლავ ხელმისაწვდომია.
- მაგიდების შექმნა/რედაქტირება/წაშლა ჩანს მფლობელისა და მენეჯერისთვის.
  დაკავებულობის შეცვლა მიმტანსაც შეუძლია; მოლარეს მაგიდების ნახვა შეუძლია.
  საბოლოო უფლებებს ისევ ბექი ამოწმებს.
- შეკვეთის გაგზავნის გაურკვეველი შედეგის შემდეგ იმავე დიალოგში ხელახლა გაგზავნა
  დაბლოკილია, განახლების შემდეგაც. დახურე დიალოგი და ჯერ შეკვეთებში გადაამოწმე შედეგი.
- დაემატა ESLint კონფიგურაცია და რეგრესიული ტესტები; მოწესრიგდა პროექტის საქაღალდეები.
- გასწორდა ანალიტიკის პერიოდის ხელახალი გამოთვლა და მოიხსნა არარსებული favicon-ის ბმული.

## შემოწმება

```powershell
npm run lint
npm run build
npm test
```

გაიარა: TypeScript/Vite build, ESLint და 33 ჩვეულებრივმა UI/API მოდულის ტესტმა.
დამატებით დროებით PostgreSQL-ზე და ოთხივე რეალურ ბექ-პროექტთან გაიარა ორმა
ინტეგრაციულმა ტესტმა: React-იდან რეგისტრაცია, ორგანიზაციისა და რესტორნის შექმნა,
თანამშრომლის მოწვევის მიღება/PIN; API მოდულებით კატალოგი, მაგიდები, კალათა,
შეკვეთა, გადახდა და ჯავშნის შექმნა/შეცვლა/გაუქმება.

`npm test` ნაგულისხმევად გამოტოვებს ამ ორ ინტეგრაციულ ტესტს. ისინი ქმნიან ანგარიშებსა
და სხვა ჩანაწერებს; `SAAS_TEST_API` გამოიყენე მხოლოდ ცალკე სატესტო ბექთან.
ტესტებში მოცემული `example.test` ანგარიშები და პაროლი ხელოვნური სატესტო მონაცემებია.

Production დამოკიდებულებების `npm audit --omit=dev` შემოწმებამ ცნობილი მოწყვლადობა
არ დააფიქსირა შემოწმების მომენტში. ეს სრული უსაფრთხოების აუდიტის გარანტია არ არის.
Build-ს რჩება მთავარი JS ფაილის ზომის გაფრთხილება (~958 KB); build წარმატებულია.
ტესტები შესრულდა jsdom-ში და ნამდვილ API-ზე; ბრაუზერის ვიზუალური ტესტი არ ჩატარებულა.

## პაროლები და პირადი ინფორმაცია

ამ გამოგზავნილ წყაროში ჩაწერილი სამუშაო პაროლი, JWT ტოკენი, ბაზის connection string
ან პირადი გასაღები ვერ ვიპოვე. `LandingPage.tsx`-ში ორი Demo ღილაკი შენს
საკონტაქტო Gmail მისამართს იყენებს. ეს მისამართი საიტის სტუმრებისთვის ჩანს.
თუ არ გინდა პირადი ელფოსტის გამოჩენა, ორივე `mailto:` შეცვალე ბიზნესის მისამართით.

პროექტის კოდი და მომხმარებლის მიმდინარე ბრაუზერის მონაცემები სხვადასხვა რამაა:
development რეჟიმში ავტორიზაციის JWT ინახება `sessionStorage`-ში, ენა — `localStorage`-ში.
ეს ბრაუზერის მონაცემები ZIP-ში არ გადმოსულა. არ გააზიარო ბრაუზერის ტოკენები,
პაროლები ან გამოჩენილი მოწვევის ტოკენები. Production რეჟიმში სესია მეხსიერებაშია
და გვერდის სრული განახლების შემდეგ ხელახლა შესვლაა საჭირო.

`VITE_` ცვლადები საიდუმლო მონაცემებისთვის არ გამოიყენო: ისინი ბრაუზერის კოდში ხვდება.
ფრონტში არ ჩაწერო Railway-ის `PGPASSWORD`, JWT signing key ან გადახდის პროვაიდერის secret.

## ინტერნეტში განთავსება

თუ ფრონტს და ბექს სხვადასხვა მისამართი აქვს, build-ის წინ მიუთითე
`VITE_API_URL=https://შენი-ბექის-მისამართი` (`/api` დამატების გარეშე).
ბექის `FRONTEND_ORIGINS`-ში დაამატე ფრონტის ზუსტი origin, მაგალითად `https://app.example.com`.
თუ ერთ origin-ზე დგას, ჰოსტინგმა `/api` რეალურ ბექზე უნდა გადაამისამართოს.
Vite-ის `server.proxy` მხოლოდ development სერვერზე მუშაობს.

## რა რჩება

ეს არქივი ავტომატურ გამოქვეყნებას არ აკეთებს. Railway-ის trial/ანგარიში არ შეცვლილა.
SaaS გამოწერის ავტომატური ჩამოჭრა, განახლება და პროვაიდერის webhooks დაკავშირებული არ არის.
ვადაგასული გამოწერისას ბექი ახალი ფილიალის დამატებას ბლოკავს, მაგრამ ჩვეულებრივი
კატალოგის ცვლილება კვლავ ნებადართულია; ამ ქცევის პოლიტიკა ცალკე დასადგენია.
რესტორნის ნაღდი/გარე ტერმინალის გადახდის ჩაწერა მუშაობს; ეს ონლაინ ბარათის ჩამოჭრა არ არის.
